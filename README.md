## Название проекта:  
Market Data Pipeline  
  
## Описание проекта:  
Minimum Viable Product (MVP) проект где проверяются разные интересные гипотезы и технологии.  
  
*Суть проекта:*  
С биржи Binance (по API через Websocket) летят отдельные сделки, их принимает программа ingestor и кладёт в Kafka, программа aggregator вычитывает сделки из Kafka, нарезает поток сделок на окна - 1 минуту и 1 секунду, преобразует их в OHLCV свечи и сохраняет их в базу (PostgreSQL). Свечи показывают изменение цены инструмента, в данном случае просто в базе данных (можно сделать графический интерфейс и следовательно реальный график, например в Grafana, но это out of scope проекта).  
  
*Детали реализации:*  
Рассматриваемые инструменты по умолчанию - валютные пары: BTC-USDT, ETH-USDT, BTC-USDC, но это не хардкод, а через переменные окружения можно задать другие.  
Минутная свеча - стандарт рынка, а секундная свеча сделана специально, чтобы нагрузить конвейер (программа исследовательская), и имеет ограниченный экономический смысл.  
Агрегация двух таймфреймов (то есть окон) дают возможность реализовать ряд интересных механик:  
- окна закрываются по независимым дедлайнам — секундное 60 раз, пока живёт одно минутное;  
- одна сделка одновременно правит два окна разной длины;  
- grace period работает по-разному: сделка, опоздавшая на 3 секунды, для секундного окна потеряна, а в минутное попадёт спокойно.  
В данном MVP проекте Kafka выглядит избыточной (всего 3 инструмента), но в боевых условиях, когда работаем с огромными потоками маркет данных, она необходима из-за возможности перечитать данные сместив оффсет, сохранения порядка сообщений, многих потребителей и др. причин.  
Сырые сделки живут исключительно в Kafka и через 24 часа удаляются, в базу сохраняются только свечи.  
В проекте два бинарника:  
cmd/  
1) ingestor/main.go    → ingestor.exe    (биржа → Kafka)  
2) aggregator/main.go  → aggregator.exe  (Kafka → свечи → PostgreSQL)  
По сути, две программы которые шарят между собой логику, но имеют разные зависимости, так сделано намерено ради независимой остановки и независимого масштабирования.  
Kafka и PostgreSQL – стандартные образы из DockerCompose, они сами поднимают дефолтные кластер и базу при запуске, см. docker-compose.yml в папке deploy, там же задаются логин\пароль от базы, Kafka идёт без аутентификации.  
Параллелизма Golang в этом MVP проекте нет, запас производительности еще на тысячи инструментов, прежде чем потребуется подключать другие ядра и потоки. Но проект создавался, в том числе, для исследования альтернативного масштабирования - в случае увеличения количества сделок\валютных пар, масштабирование достигается запуском дополнительных инстансов aggregator - Kafka раздаст партиции между экземплярами, и обработка пойдёт шире.  
  
*Архитекстура Кафки:*  
Ingestor >продюсер	> пишет сделки в md.trades  
Aggregator > консьюмер > читает md.trades  
Aggregator >продюсер > пишет закрытые свечи в md.candles  
В топиках md.trades и md.candles по 4 партиции в демонстрационных\исследовательских целях, через них достигается параллелизм работы, и в kafka UI (после запуска по умолчанию доступен по http://localhost:8080/) можно посмотреть на ребалансировку при запуске второго агрегатора.  
  
## Требования: 
- Docker с плагином compose  
- Go 1.25+  
- `make` — опционально, все команды можно вызывать напрямую  
`golang-migrate` устанавливать не нужно: миграции запускаются в контейнере.  
  
## Запуск:   
Управляем проектом через Makefile, для windows надо установить, если его нет - winget install ezwinports.make  
### Коротко:  
1) Запустить Docker Compose  
2) make up            # инфраструктура и топики  
3) make migrate-up    # создать таблицу candles  
4) Темринал1: make ingestor    #получаем сделки с биржи  
5) Терминал2: make aggregator  #создаем свечи и пишем в базу  
  
### Подробно:  
*1. Инфраструктура*  
```bash  
make up  
# а если без make то:  
docker compose -f deploy/docker-compose.yml up -d  
```  
Поднимутся Kafka (KRaft, без ZooKeeper), PostgreSQL и Kafka UI. Топики  
`md.trades` и `md.candles` создаются автоматически одноразовым сервисом  
`kafka-init`.  
  
Kafka UI: http://localhost:8080 — оба топика по 4 партиции.  
  
*2. Миграции*  
```bash  
make migrate-up  
```  
  
*3. Ingestor*  
Терминал 1:  
  
```bash  
make ingestor  
# а если без make то:  
go run ./cmd/ingestor  
```  
  
Через секунду появится подключение, дальше раз в 10 секунд — сводка:  
  
```json  
{"msg":"feed stats","received":723,"published":723,"duplicates":0,"dropped":0,"queue":0}  
{"msg":"per symbol","BTC-USDC":27,"BTC-USDT":294,"ETH-USDT":402}  
```  
  
*4. Проверка топика*  
Терминал 2:  
  
```bash  
make consume-trades  
```  
  
Должны побежать JSON-сделки с ключами-символами. Прервать через Ctrl+C.  
  
*5. Aggregator*  
Терминал 2:  
  
```bash  
make aggregator  
```  
  
Первые секундные свечи появятся через несколько секунд, минутные — на
ближайшей границе минуты:  
  
```json  
{"msg":"candle closed","symbol":"BTC-USDT","tf":"1m","open_time":"2026-09-06T11:44:00Z",  
 "o":"79951.99","h":"79953.92","l":"79951.98","c":"79953.92","v":"0.9055","n":436}  
```  
  
Секундные свечи пишутся на уровне Debug — их до трёх в секунду, иначе  
консоль зальёт. Показать: `MDP_LOG_LEVEL=debug`.  
  
*6. Проверка базы*  
```bash  
make psql  
```  
  
```sql  
SELECT symbol, open_time::time AS t, open, high, low, close, volume, trade_count  
FROM candles WHERE timeframe = '1m'  
ORDER BY open_time DESC, symbol LIMIT 10;  
```  
  
*Остановка*  
```bash  
make down                                           # тома с данными остаются  
docker compose -f deploy/docker-compose.yml down -v # вместе с данными  
```  
  
## Конфигурация:  
Только переменные окружения, без файлов конфига. Невалидное значение —  
падение на старте с внятным сообщением, а не тихая подстановка умолчания.  
  
| Переменная | По умолчанию | Сервис |  
|---|---|---|  
| `MDP_SYMBOLS` | `BTC-USDT,ETH-USDT,BTC-USDC` | ingestor |  
| `MDP_TIMEFRAMES` | `1s,1m` | aggregator |  
| `MDP_KAFKA_BROKERS` | `localhost:9092` | оба |  
| `MDP_TOPIC_TRADES` | `md.trades` | оба |  
| `MDP_TOPIC_CANDLES` | `md.candles` | aggregator |  
| `MDP_CONSUMER_GROUP` | `md-aggregator` | aggregator |  
| `MDP_BINANCE_WS_URL` | `wss://stream.binance.com:9443/stream` | ingestor |  
| `MDP_POSTGRES_DSN` | `postgres://marketdata:marketdata@localhost:5432/marketdata?sslmode=disable` | aggregator |  
| `MDP_GRACE_PERIOD` | `2s` | aggregator |  
| `MDP_IDLE_TIMEOUT` | `3s` | aggregator |  
| `MDP_LOG_LEVEL` | `info` | оба |  
  
Инструменты меняются без пересборки — маппинг на тикеры биржи строится  
автоматически (`SOL-USDT` → `solusdt@trade`):  
  
```bash  
MDP_SYMBOLS="SOL-USDT,DOGE-USDT" go run ./cmd/ingestor  
```  
  
## Структура:  
```  
cmd/  
├── ingestor/          Binance → Kafka  
└── aggregator/        Kafka → окна → PostgreSQL + Kafka  
internal/  
├── domain/            Symbol, Timeframe, Trade, Candle — без внешних зависимостей  
├── feed/              интерфейс Feed  
│   └── binance/       WebSocket, реконнект, дедупликация, разбор сообщений  
├── broker/kafka/      продюсер, консьюмер, формат сообщений  
├── aggregate/         окна и их закрытие по дедлайнам  
├── storage/postgres/  пул соединений, идемпотентный upsert  
└── config/            чтение окружения  
migrations/            схема БД  
deploy/                docker-compose  
```  
  
Домен не зависит ни от Kafka, ни от базы, ни от биржи: маппинг  
`BTC-USDT` ↔ `btcusdt` живёт только в адаптере биржи.
